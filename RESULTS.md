## 4. Conclusion and limitations
- Hypothesis "fewer errors, same speed": the result was **same speed, and errors drop substantially in proportion to the contracts written**.
- Ultimately the effect of this language depends on how strongly the AI writes contracts. The next step is to make aggregates like sum and max usable in contracts (specification functions).
- Limitations: the 10 problems are easy. There is only one model as the worker. Mutation testing was run only on solutions I wrote. The compiler (written by me) has not yet been audited. If the verifier has a soundness bug, the numbers change.

## 5. Stage 2: aggregates for contracts (2026-11-10)
Syntax `sum/count/max/min(k in lo..hi: e)` (SPEC §6). The aggregate is treated as an undefined z3 function F(lo, hi, outer bound variables),
and at each place it is used, "unfold one step" facts (shrinking/extending the upper and lower ends, sum·count empty range = 0) are added as lemmas.
Ends containing a bound variable are not moved, which prevents matching loops. The proof is first attempted without lemmas, and if that fails the lemmas are added and it is retried.

| | 1st round (no contracts, mutants.json) | Aggregate-contract implementation (mutants3.json) |
|---|---|---|
| Mutants wrong under tests | 79 | 79 |
| └ Vow rejects at compile time | 73 (92%) | **79 (100%)** |
| └ of those, rejected by timeout (verify_unknown) | 0 | 0 |
| Rejections among same-behavior mutants (false positives) | 1 / 4 | 1 / 4 (same p02 `i = 1`→`0`) |

- Solutions: `bench/solutions/vow_agg/` (aggregate ensures·invariants added to vow_try1 only for p01·p06·p07·p09). All 4 proved in 0.1~0.3 seconds, re-grading 10/10.
- It catches all 6 that were previously missed (p01 `+`→`-`, p06 `cur + v`→`cur - v`, p07 `<`→`<=`·`c + 1`→`c`, p09 `+`→`-`·`*`→`+`).
- p06 (maximum subarray sum) cannot be proved when written with `max` (an inductive fact like "max(e + c) = max(e) + c" is needed). Instead,
  writing it as "greater than or equal to every partial sum (forall) and equal to one of them (exists)" makes it provable.
- The intermediate implementation (which put lemmas into every proof, mutants2.json) also caught 79/79, but 4 p06 mutants were rejected by timeout
  and so had no counterexample. After splitting the proof into two passes, that became 0.
- Regression suite: tests/must_reject 20/20 still rejected, examples unchanged. 5 deliberately wrong aggregate contracts (outer-variable body, nested aggregate, empty max, etc.) were all rejected.
- Audit (Claude sonnet): soundness must-fix 0; after the fixes, the confirmation audit had must-fix 0. Both audits judged only by reading code because the shell was blocked, and I did the reproduction with the tests above.
- Limitation: because unfolding is one step per place, correct contracts that compute several steps of a fixed range, like `sum(k in 0..3: j) == 3*j`, cannot be proved (timeout).
  Facts such as middle element of a range <= max, or splitting a sum at an arbitrary point, are also not known automatically. I wrote the aggregate contracts myself. Whether an independent AI writes aggregate contracts on its own has not yet been measured.

## 6. Stage 0: safe mode and public function boundary checks (2026-11-10)
Two holes fixed:
1. With `--no-verify` (no proving), it still emitted `get_unchecked` and silently wrapping arithmetic → safe mode: checks indexing, arithmetic, and alloc size and panics on violation (`vow: index out of bounds`, `vow: arithmetic error`). `/` `%` use the same domain as the verifier (divisor > 0, dividend >= 0).
2. Nothing stopped Rust code from calling a generated `pub fn` in violation of requires → a function with requires becomes `pub fn f` (checks requires at run time, `vow: requires violated`) + a private `f__vow_body`. In proof mode, inner calls go directly to the body. Contracts are evaluated in i128 with Euclidean division. `--trust-callers` turns off the check.

- Tests: `tests/run_all.py` 57/57 (reject 24, examples in three modes 10, runtime 23).
- Audit (Claude) must-fix 2: generated temporary names (`vow_k1`, `vow_i`) shadowed user variables of the same name, bypassing the requires check, and in proof mode an out-of-range `get_unchecked` (abnormal termination reproduced); safe-mode array writes wrote wrong values. → The parser now rejects names with the `vow_` prefix or containing `__` (`reserved_name`).
- Confirmation after the fix (Claude) must-fix 0. Rust keywords and `_` names (rustc compile failure), which had been recommendations, were also rejected as reserved words, and I directly reproduced and fixed that the contract helper did not compile under Rust 2015 (the default of `rustc -O x.rs`) (`usize::try_from`).
- Mutation testing (`bench/mutants4.json`, vow_agg): 79/79 rejected, false positives 1/4 unchanged. As the reference build (`--no-verify`) became safe mode, 9 mutants that had been timeouts (undefined-behavior infinite loops, etc.) turned into `wrong` (panic).
- Speed (vow_agg, ms, median of 21 runs): with `--trust-callers` it is the same as before (within error of the Rust reference). With checks on, problems with an element-range forall get slower (p01 0.20→1.13, p05 0.30→0.76, p09 0.43→1.20). p04 writes its sortedness precondition as a double forall, making an O(n^2) check at n=10^6, so the performance stage timed out. Speed comparisons are measured with `--trust-callers`.
- Remaining: replace heavy requires (sorting, etc.) with an O(n) check of the same meaning (a proven equivalence transformation), a length upper bound for numeric-range quantifiers, and also putting the contract domain (out-of-range indices, etc.) into verifier proof obligations to align meaning with the runtime check.

## 7. M1 = C2: LLVM IR backend (2026-11-10)
`vowc --backend llvm` emits text LLVM IR (`.ll`) and Rust bindings (`.rs`) together. The runtime support code is `vowc/runtime.c`, compiled by clang. The spec is in `docs/M1_LLVM_SPEC.md`. The reference is the Rust backend (`codegen.py`), which was not modified.
- The test harness keeps the Rust driver as is and puts the bindings into `mod sol`. The two object files (gen.o, rt.o) are attached to rustc as link-args. Returned arrays are allocated with the Rust allocator and passed as `Vec` without copying.
- Regression suite (`tests/run_all.py --backend both`) 102/102 (110/110 after wrap-up, 33 runtime tests)
  - Reject 24, and per backend examples 10, runtime 29.
  - New tests r24·r25: evaluation order. r26~r29: array deallocation paths. The deallocation-path tests use runtime.c `-DVOW_COUNT_ALLOCS` to check that the allocation count equals the free count.
- Proof facts in the IR
  - Proof-mode body: arithmetic is `add/sub/mul nsw`, array access is `getelementptr inbounds`, division is `udiv/urem` (the verifier proves the domain).
  - Array arguments: `noalias nocapture readonly`. The basis is the ownership rule of check.py (no modifying, storing, or returning arguments).
  - Safe-mode bodies have no `nsw` (confirmed by test).
- bench vow_agg `--trust-callers`: 10/10 on both backends.
  - Speed was compared against the Rust reference inside the same executable, because the reference time fluctuates between runs.
  - Same: p01·p02·p05·p06·p07·p10, p08 (0.20ms vs 0.20ms after fixing it to a zero-initialized allocation).
  - LLVM faster: p03 (1.17x relative to the reference, Rust implementation 1.48x), p09 (0.79x, Rust implementation 1.0x).
  - **LLVM slower: p04 by 4~5%.** Measured twice. Rust implementation 33.4~33.5ms, LLVM implementation 34.9~35.3ms. It is a problem that makes a million calls. I presumed it is because the Rust driver cannot inline a function across the FFI boundary, and did not verify this. This one problem fails to meet the M1 speed criterion (within error or faster).
- Mutation testing (`bench/mutants5_llvm.json`, build before the audit fixes)

  - 4 test results differ, where a Rust implementation timeout became `wrong` in the LLVM implementation. They are `i = i + 1`→`i = i` in p01·p05·p09, and `lo < hi`→`lo <= hi` in p04.

## 9. Stage 0 remaining tasks: contract domain·runtime iteration budget·O(n) sortedness precondition (2026-11-10)
Decision `docs/M0_CONTRACTS.md` (design draft by Codex gpt-6-astra, revised by the main agent), spec `SPEC.md` §6·6a·7.
1. **Contract domain as verifier proof obligations.** Inside contracts, `a[i]` (range), `/` `%` (divisor != 0, contract division is Euclidean), `some_val`·`ok_val`·`err_val` (tag), and empty `max`/`min` (lo < hi) are proved in short-circuit·quantifier reach order (new error code `contract_domain`, variant_field uses the existing `variant_domain`). requires is proved using only earlier requires; ensures·invariant use clauses of the same kind up to the previous one. Now, for proven programs, the public function runtime check no longer produces `requires undefined` because of the domain.
   - Only the variant_field domain goes into assumptions. Assuming other domains as well loaded nested-quantifier index ranges into every query, and the p06 proof went from 0.44 seconds to 69 seconds (0.61 seconds after reverting).
   - The callee requires domain is not re-proved at the call site (the callee proves it, audit recommendation).
   - Intended semantic change: unguarded `max`·`variant_field` requires (r20, g1_r06) are rejected in default mode. The two runtime tests use `--no-verify` only, and r21 is preceded by `len(a) >= 1`.
2. **Runtime iteration budget.** Instead of a static upper bound, the entire requires check at a single public function entry shares 2^30 quantifier·aggregate iterations. If exceeded, `vow: requires undefined: contract iteration budget exceeded` (101, both backends). Expressions skipped by empty ranges·short-circuiting do not consume it.
3. **Sortedness precondition O(n).** `forall i in 0..len(a): forall j in i(+1)..len(a): a[i] <= a[j]` is recognized by AST (`codegen.match_sorted_requires`) and only the runtime check loops with `a[k-1] <= a[k]`. Both backends convert it the same way wherever it is in the expression (right of a short-circuit, inside an outer quantifier). The verifier uses the original expression. At 200,000 elements the double form exceeds the budget while the converted form passes (`sort_nested_big`).

## 12. Removing the LLVM proof build re-verification in the fuzzer (2026-11-10)
1. **Problem**: because the fuzzer (`bench/fuzz/run.py`) called vowc separately per backend, the LLVM build (`--backend llvm --rust-bindings` in `prep_llvm`) of a program that passed verification ran once more the z3 verification already done in phase_a.
2. **Fix**: a hidden test option `--also-llvm LL RS` in vowc (`vowc/vowc.py`, outside SPEC and not in help, like `--contract-budget`). It is accepted only on the Rust backend, and with the same parsing·checking·verification done once, it writes the Rust output together with the LLVM IR·bindings. ## 32. B++: rlimit exhaustion of an inference search query drops only the candidate (2026-11-11)

## 44. Performance check: why p03, p04 and p08 were 1.3–1.5× slower than Rust (2026-11-12)

Measured with `bench/harness/run.py bench/solutions/pruv_agg --pruv --backend {rust,llvm} --trust-callers`, n=10⁶ (p04/p10: 10⁶ queries), median of 21 runs per execution, p03/p04/p08 repeated 3 times (ratio = median of the three). The machine was loaded (`uptime` load average 3–5), so single values move by up to ±30%; Apple arm64 only.

| Problem | Rust backend sol/ref | LLVM backend sol/ref | Hand-written Rust (`rust_try1`) sol/ref |
|---|---|---|---|
| p03 `is_sorted` | 1.47 | 1.16 | ~1.0 (uses `for i in 1..len`) |
| p04 `binary_search` | 1.44 | 1.50 | ~1.6 (same `lo < hi` algorithm) |
| p08 `reverse` | 1.34 | 1.33 | 1.3–1.4 (`vec![0; n]` + index loop) |
| p01, p10 (controls) | 1.00, 1.02 | 1.0, 1.00 | |

Causes (evidence: generated `.rs`/`.ll`, `--emit asm`, micro-benchmarks):
- **p04 is the algorithm, not the translator.** The generated loop has no bounds or overflow checks and compiles to branch-free `csel`. The reference (`partition_point`) halves a `size`, so the loop-carried dependency does not go through the loaded value; the Pruv solution moves both `lo` and `hi`. The same Pruv source rewritten in the halving form ran 23.8 ms vs reference 26.6 ms (n=10⁶). Hand-written Rust with `lo < hi` is equally slow. Option is returned in registers (x0/x1) on the LLVM backend, so the FFI boundary is not the cause (this disproves the earlier "FFI cannot be inlined" guess).
- **p08 is the zero-initialized allocation.** `alloc(n, 0)` lowers to `vec![0; n]` (`__rust_alloc_zeroed`) on the Rust backend and to `pruv_alloc(len, 0)` → calloc in `pruvc/runtime.c` on the LLVM backend; the copy loop itself is NEON-vectorized like the reference. sol − ref ≈ 0.036 ms ≈ the measured calloc cost 0.033 ms. The reference uses an uninitialized `with_capacity` + `collect`.
- **p03 is the only translator-shaped cause, and only on the Rust backend.** `while i < len { if a[i-1] > a[i] { return false; } i = i + 1; }` (emitted as is by `pruvc/codegen.py` `While` and `pruv-core/src/codegen.rs` `Stmt::While`) is compiled by rustc into a loop that materializes the return value inside the loop with two branches; a hand-written `usize` while loop of the same shape is equally slow, while `for i in 1..len` matches the reference. The LLVM backend output already has the reference shape (`ldp` + one compare branch); the remaining 1.16× is within the noise of this loaded machine (unconfirmed).

Decisions:
- No compiler change in this batch. p04 needs no compiler change (the faster form is a different algorithm a user can write). p08 would need a language-level "allocate without initialization" or a proof that the whole array is overwritten; the gain is ~0.035 ms per 10⁶ elements, so it is deferred to G8/G5 (owned containers). p03 would need a `while` → `for` rewrite in the Rust-source backend only; the LLVM backend (the long-term path) does not need it, so it is deferred.
- Still open from the roadmap line: passing more proof facts (value ranges, non-overlap) to LLVM — not measured here because none of the three gaps came from missing facts.
- Not measured: a quiet machine, x86-64/Linux/Windows, default mode (without `--trust-callers`).
