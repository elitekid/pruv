# G5 problems (inout parameters)

Each solution is a small Pruv project in a directory `qNN/`; the compiler is started on `qNN/root.pruv`. The language
rules are in SPEC.md and docs/G5_SPEC.md (sections 2-6: `inout` parameters and call markers, exclusive access, `old(a)`,
statement-boundary calls, host entries). Nothing else is needed.

Rules common to both problems:

- The **root file** `root.pruv` contains the **host entries**: root `pub`, non-generic functions with exactly the given
  names, types, effects and contracts (copy the lines exactly; you may not weaken, drop or add `requires`/`ensures`, and
  the root may not contain other `pub fn`, except an optional `pub fn main() -> ()`). Root-private helpers are allowed.
- A host entry is an ordinary function (G5 does not expose `inout` to the host): it owns a copy of its input
  (`let mut w: [T] = copy(a);`), updates it **in place** through `inout` helpers (`f(inout w, ...)`), and returns it. The
  work between the copy and the return must not copy or allocate again.
- The entry contracts are **exact**: they state the full content and the frame of the result (every element, written or
  untouched), not only its length or range. The `inout` helpers need contracts with `old(a)` strong enough for the entries
  to prove theirs; the proof is modular (a caller sees only the helper's contract).
- The project must verify (no `--no-verify`) on both compilers and on both backends, and must not panic on the test
  inputs. Host entries check their `requires` at run time; the tests only call them with arguments that satisfy `requires`.
- The grader compares the entries' results (Rust `Debug` text) with a trusted reference computed in Python.

Type mapping at the host boundary: `i64` is `i64`, `[i64]` is `&[i64]` in and `Vec<i64>` out, `[u8]` is `&[u8]` in and
`Vec<u8>` out.

Build configurations: the Python and the Rust compiler, each with the Rust backend and with the LLVM backend (four
configurations). All four must give the reference results.

Test inputs are generated by `tests()` in `run.py` (seeded).

## q01 - bounded byte-range transformation

Files: `root.pruv` only.

Host entries (exactly these lines; every one is `! alloc`):

```pruv
pub fn add_sat(a: [u8], lo: i64, hi: i64, c: i64) -> [u8] ! alloc
  requires 0 <= lo && lo <= hi && hi <= len(a) && 0 <= c && c <= 255
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): (lo <= k && k < hi && a[k] + c <= 255) ==> result[k] == a[k] + c
  ensures forall k in 0..len(a): (lo <= k && k < hi && a[k] + c > 255) ==> result[k] == 255
  ensures forall k in 0..len(a): (k < lo || k >= hi) ==> result[k] == a[k]

pub fn add_wrap(a: [u8], lo: i64, hi: i64, c: i64) -> [u8] ! alloc
  requires 0 <= lo && lo <= hi && hi <= len(a) && 0 <= c && c <= 255
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): (lo <= k && k < hi) ==> result[k] == (a[k] + c) % 256
  ensures forall k in 0..len(a): (k < lo || k >= hi) ==> result[k] == a[k]

pub fn fill_bytes(a: [u8], lo: i64, hi: i64, v: i64) -> [u8] ! alloc
  requires 0 <= lo && lo <= hi && hi <= len(a) && 0 <= v && v <= 255
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): (lo <= k && k < hi) ==> result[k] == v
  ensures forall k in 0..len(a): (k < lo || k >= hi) ==> result[k] == a[k]
```

- `add_sat`: add `c` to every element of the half-open range `lo..hi`, saturating at 255; every other element is
  unchanged.
- `add_wrap`: add `c` to every element of `lo..hi` modulo 256; every other element is unchanged.
- `fill_bytes`: set every element of `lo..hi` to `v`; every other element is unchanged.
- Structure required by the grader: `root.pruv` has at least one private helper with an `inout [u8]` parameter, at least
  four `inout` occurrences, an `old(...)` in a helper contract, and `copy(...)` in the wrappers; no `pub fn` takes `inout`.
  Both the per-range loops and the per-element updates are expected to be `inout` helpers (an element update helper, a
  range helper that loops and calls it), with exact `old(b)` content/frame contracts.
- Tests: about 15 arrays of bytes (empty, singletons, boundary values 0/255, runs near saturation, six random arrays of
  length 4..=12, one of length 300); up to eight valid windows per array (`(0,0)`, `(0,n)`, `(n,n)`, `(1,n)`, `(0,n/2)`,
  `(n/2,n)`, `(1,n-1)`, `(n/3,2n/3)`); `c` in `{0, 1, 100, 255}`, `v` in `{0, 77, 255}`.
  Example: `add_sat([250, 3, 7, 9], 0, 3, 10) == [255, 13, 17, 9]`, `add_wrap([250, 3, 7, 9], 0, 3, 10) == [4, 13, 17, 9]`,
  `fill_bytes([1, 2, 3, 4], 1, 3, 9) == [1, 9, 9, 4]`.

Reference behaviour in Python:

```python
def add_sat(a, lo, hi, c):  return [min(255, x + c) if lo <= k < hi else x for k, x in enumerate(a)]
def add_wrap(a, lo, hi, c): return [(x + c) % 256 if lo <= k < hi else x for k, x in enumerate(a)]
def fill_bytes(a, lo, hi, v): return [v if lo <= k < hi else x for k, x in enumerate(a)]
```

## q02 - module-based recursive array transformation

Files: `root.pruv` (declares `mod xform;`) and `xform.pruv`.

Host entries (exactly these lines; every one is `! alloc`):

```pruv
pub fn reverse_window(a: [i64], lo: i64, hi: i64) -> [i64] ! alloc
  requires 0 <= lo && lo <= hi + 1 && hi < len(a)
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): (lo <= k && k <= hi) ==> result[k] == a[lo + hi - k]
  ensures forall k in 0..len(a): (k < lo || k > hi) ==> result[k] == a[k]

pub fn reverse_all(a: [i64]) -> [i64] ! alloc
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): result[k] == a[len(a) - 1 - k]

pub fn shift_tail(a: [i64], i: i64, d: i64) -> [i64] ! alloc
  requires 0 <= i && i <= len(a) && -1000 <= d && d <= 1000
  requires forall k in 0..len(a): -1000000 <= a[k] && a[k] <= 1000000
  ensures len(result) == len(a)
  ensures forall k in 0..len(a): k >= i ==> result[k] == a[k] + d
  ensures forall k in 0..len(a): k < i ==> result[k] == a[k]
```

- `reverse_window`: reverse the inclusive window `lo..=hi` (empty when `hi == lo - 1`); everything outside is unchanged.
- `reverse_all`: reverse the whole array.
- `shift_tail`: add `d` to every element from index `i` on; the elements before `i` are unchanged.
- The recursive in-place functions live in the child module `crate::xform` (reached from the root by `crate::xform::`
  paths) as `pub` Pruv-only helpers with an `inout [i64]` parameter. At least two of them are recursive (each with a
  `decreases` clause) and state exact `old(a)` content and frame contracts; the root wrappers only copy, call and return.
- Structure required by the grader: `root.pruv` declares `mod xform;`, reaches it with `crate::xform::` paths and uses
  `copy(...)`; `xform.pruv` has a `pub fn` with an `inout [i64]` parameter, at least two `decreases` clauses, a function
  that calls itself with `inout`, and `old(...)` in its contracts.
- Tests: ten arrays for the reversals (empty, singletons, short ones, one with `i64::MIN`/`i64::MAX`/small values, one of
  length 40, one of length 500), every valid window of a fixed list per array; eight arrays with elements in
  `-1000000..=1000000` for `shift_tail` (lengths 0..=500), `i` in `{0, n/2, n}`, `d` in `{-1000, 0, 7, 1000}`.
  Example: `reverse_window([1,2,3,4,5], 1, 3) == [1,4,3,2,5]`, `reverse_all([1,2,3]) == [3,2,1]`,
  `shift_tail([1,2,3], 1, 10) == [1,12,13]`.

Reference behaviour in Python:

```python
def reverse_window(a, lo, hi): return [a[lo + hi - k] if lo <= k <= hi else x for k, x in enumerate(a)]
def reverse_all(a): return a[::-1]
def shift_tail(a, i, d): return [x + d if k >= i else x for k, x in enumerate(a)]
```
