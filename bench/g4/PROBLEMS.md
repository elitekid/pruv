# G4 problems (modules, visibility and host entries)

Each solution is a small multi-file Pruv project in a directory `qNN/`; the compiler is started on `qNN/root.pruv`. The
language rules are in SPEC.md (section 6f, Modules and visibility; sections 3-7 for functions, arrays, contracts and
what is proved; section 6e for recursion and recursive types). Nothing else is needed.

Rules common to both problems:

- The **root file** `root.pruv` contains the **host entries**: root `pub`, non-generic functions with exactly the given
  names, types, effects and contracts (copy the lines exactly; you may not weaken, drop or add `requires`/`ensures`, and
  the root may not contain other `pub fn`, except an optional `pub fn main() -> ()`). Root-private helpers are allowed.
- Everything else lives in **child modules** at the given paths. Reach other modules only by absolute paths
  (`crate::store::find(a, q)`); there is no `use`. Children may have `pub` items (callable from Pruv only) and private
  helpers. A public signature or contract may mention only public items.
- The project must verify (no `--no-verify`) on both compilers and on both backends, and must not panic on the test
  inputs. The proof is modular: a caller sees only the callee's contract, never its body, so the child contracts
  must be strong enough for the root entries to prove theirs.
- The grader compares the entries' results (Rust `Debug` text) with a trusted reference computed in Python. Host entries
  check their `requires` at run time; the tests only call them with arguments that satisfy `requires`.

Type mapping at the host boundary: `i64` is `i64`, `[i64]` is `&[i64]`.

Build configurations: the Python and the Rust compiler, each with the Rust backend and with the LLVM backend (four
configurations). All four must give the reference results. With the LLVM backend the host program calls the typed
bindings generated with `--rust-bindings` (they call the raw `pruv_abi_<entry>` symbols); with the Rust backend it calls
the generated `pub fn` entries.

Test inputs are generated by `tests()` in `run.py` (seeded).

## q01 - bounded array service in modules

Files: `root.pruv` (declares `mod store;`), `store.pruv` (declares `mod check;`), `store/check.pruv`.

Root host entries (all three with exactly these lines):

```pruv
pub fn find_first(a: [i64], q: i64) -> i64
  requires len(a) <= 1000
  ensures result == 0 - 1 || (0 <= result && result < len(a))
  ensures result >= 0 ==> a[result] == q && (forall k in 0..result: a[k] != q)
  ensures result < 0 ==> (forall k in 0..len(a): a[k] != q)

pub fn sum_range(a: [i64], lo: i64, hi: i64) -> i64
  requires len(a) <= 1000
  requires forall k in 0..len(a): -1000000 <= a[k] && a[k] <= 1000000
  ensures (0 <= lo && lo <= hi && hi <= len(a)) ==> result == sum(k in lo..hi: a[k])
  ensures !(0 <= lo && lo <= hi && hi <= len(a)) ==> result == 0 - 1

pub fn insert_get(a: [i64], i: i64, v: i64, j: i64) -> i64 ! alloc
  requires len(a) <= 1000
  ensures (0 <= i && i <= len(a) && 0 <= j && j <= len(a)) ==> ((j < i ==> result == a[j]) && (j == i ==> result == v) && (j > i ==> result == a[j - 1]))
  ensures !(0 <= i && i <= len(a) && 0 <= j && j <= len(a)) ==> result == 0 - 1
```

- `find_first`: the smallest index `k` with `a[k] == q`, or `-1`.
- `sum_range`: the sum of `a[lo..hi]` (half-open) when `0 <= lo <= hi <= len(a)`, otherwise `-1` (an invalid range is
  not an error; it is answered with `-1`).
- `insert_get`: conceptually insert `v` into `a` at position `i` (the result has `len(a) + 1` elements, `v` at index `i`,
  the old elements after it shifted by one) and return the element at index `j` of that new array. `-1` when `i` is not
  in `0..=len(a)` or `j` is not in `0..=len(a)`. The new array must really be built (with `alloc`) and then read.
- Structure required by the grader: `root.pruv` declares `mod store;`; `store.pruv` declares `mod check;` and has at
  least one private (non-`pub`) helper function and at least one `pub fn`; `store/check.pruv` has at least one `pub fn`;
  `root.pruv` reaches the children with `crate::store::` paths. The module paths, the helpers' names and their contracts are
  your choice, but the root entries may only call into the children (the bounds checks live in `crate::store::check`).
- Tests: about 15 arrays with elements in `-1000000..=1000000` (empty, singletons, small arrays with repeats, random
  arrays of length 2..=9, one of length 40, one of length 1000). `find_first` with ten values of `q` (including
  `i64::MIN` and `i64::MAX`); `sum_range` with eleven ranges per array, valid and invalid (`(0,0)`, `(0,n)`, `(1,n)`,
  `(n/2,n)`, `(n,n)`, `(-1,0)`, `(0,n+1)`, `(n+1,n+1)`, `(2,1)`, `(MIN,0)`, `(0,MAX)`); `insert_get` with the positions
  `i` in `{0, n/2, n, -1, n+1}`, `j` in `{0, i, i+1, n, n+1, -1}` and `v` in `{42, MIN, MAX}` (small arrays only; `42`
  for the longer ones).
  Example: `find_first([5,3,9,3], 3) == 1`, `sum_range([1,2,3,4], 1, 3) == 5`, `sum_range([1,2], 0, 3) == -1`,
  `insert_get([10,20,30], 1, 99, 2) == 20`, `insert_get([10,20,30], 1, 99, 1) == 99`.

## q02 - recursive tree service with scalar host wrappers

Files: `root.pruv` (declares `mod tree;`), `tree.pruv` (declares `mod shape;`), `tree/shape.pruv`.

Root host entries (all three with exactly these lines; every one is `! alloc`):

```pruv
pub fn node_total(n: i64) -> i64 ! alloc
  requires 0 <= n && n <= 1000
  ensures result == n

pub fn leaf_total(n: i64) -> i64 ! alloc
  requires 0 <= n && n <= 1000
  ensures result == n + 1

pub fn tree_height(n: i64) -> i64 ! alloc
  requires 0 <= n && n <= 1000
  ensures 0 <= result && result <= 2 * n + 1
```

- The child module `crate::tree` defines `enum Tree { Empty, Node(value: i64, left: Tree, right: Tree) }` as a `pub`
  type and the recursive functions over it, each with `decreases size(t)`; the range split used when building the tree is
  in `crate::tree::shape`. A recursive type cannot be part of a host entry (SPEC 6e/6f), so the root entries take and
  return `i64` and build the tree internally (a root-private helper may return it).
- Every entry builds the **balanced** tree of the integers `0..n` (one `Node` per integer, `Empty` leaves): the node for
  the range `lo..hi` (`lo < hi`) holds the value `mid = lo + (hi - lo) / 2`, its left subtree is the tree of `lo..mid`
  and its right subtree the tree of `mid + 1..hi`; an empty range is `Empty`. Then it computes its result by a recursive
  walk over that tree: `node_total` counts the `Node`s, `leaf_total` counts the `Empty` leaves, `tree_height` is the
  height (`Empty` has height 0, a `Node` has `1 + max(height(left), height(right))`). No entry may compute its result
  from `n` directly.
- The `tree_height` contract is deliberately weak (the exact height is a recursive property that cannot be stated with
  the contract operations); the grader checks the exact heights of the balanced tree.
- Structure required by the grader: `root.pruv` declares `mod tree;`; `tree.pruv` declares `mod shape;`, contains
  `enum Tree`, a `match`, and at least three `decreases size(` clauses; `tree/shape.pruv` has at least one `pub fn`;
  `root.pruv` reaches the children with `crate::tree::` paths and defines no `enum`.
- Tests: `n` over `{0..9, 15, 16, 17, 31, 32, 100, 127, 128, 500, 999, 1000}` plus ten random values in `0..=1000`,
  each with all three entries. Example: `node_total(3) == 3`, `leaf_total(0) == 1`, `tree_height(3) == 2`,
  `tree_height(4) == 3`.
